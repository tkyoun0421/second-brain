# 자동 중요도 기반 메모리 캡처

`brain_capture_auto_memory`는 작업 중 나온 **결정** 또는 **오류/해결 경험**을 후보로 받아,
중요도를 계산한 뒤 보관 여부를 자동으로 결정합니다. 이 기능은 대화 전문이나 원본 로그를
저장하지 않습니다.

## 판정 규칙

점수는 다음 다섯 신호로 계산합니다.

| 신호 | 범위 | 의미 |
| --- | --- | --- |
| 재사용성 | 0–3 | 다음 작업에서도 도움이 되는가 |
| 영향도 | 0–3 | 배포·보안·데이터·프로젝트 규칙에 미치는 영향 |
| 적용 범위 | 0–2 | 일회성인지, 지속되는 범위인지 |
| 근거 | 0–2 | 사용자 발언·테스트·실행 결과로 뒷받침되는 정도 |
| 노이즈 감점 | 0–3 | 일시적·중복·무관한 정보인지 |

`재사용성 + 영향도 + 적용 범위 + 근거 - 노이즈 감점`이 4점 미만이면 `discarded`로
응답하고 DB에는 후보 자체를 남기지 않습니다. 4점 이상이면 `proposed` 메모리로
Memory Inbox에 저장합니다. 높은 중요도라도 자동으로 `confirmed`나 `verified`가 되지
않습니다.

## 저장 안전장치

- 민감정보 검사에 걸리면 저장 전에 요청을 거절합니다.
- 동일한 종류·문장·범위는 관측 시각이 달라도 같은 `auto_capture_key`를 사용합니다.
  DB의 owner별 unique index가 중복 저장을 막고, 기존 항목을 `duplicate`로 돌려줍니다.
- 자동 캡처는 `memory:propose` 권한만 사용합니다. 확정은 기존의 명시적 사용자 확인,
  검증은 테스트 또는 실행 근거가 있어야 합니다.
- Inbox는 자동 캡처의 중요도 높은 순서로 보여 주며, 수동 제안 항목은 그 뒤에 표시합니다.

## 자동화의 경계

MCP 서버는 Codex의 모든 대화를 직접 볼 수 없습니다. 따라서 실제 자동화는 MCP 호스트나
에이전트의 작업 체크포인트에서 이 도구를 호출할 때 동작합니다. 권장 시점은 다음과 같습니다.

1. 사용자가 장기적으로 유지할 선택을 명시했을 때
2. 오류의 원인·해결·검증 결과가 갖춰졌을 때
3. 작업 종료 시 재사용 가능한 결과를 요약했을 때

단순 질의, 임시 추측, 한 번의 재시도, 원본 로그 전체는 후보로 보내지 않습니다.

## 운영 적용 순서

1. `supabase/migrations/20260731000900_automatic_memory_capture.sql`을 Supabase SQL Editor에서 실행합니다.
2. Railway가 이 변경을 배포한 뒤 `GET /v1/health`를 확인합니다.
3. 로컬 MCP를 새로 시작해 `brain_capture_auto_memory` 도구가 보이는지 확인합니다.
4. 실제 작업 체크포인트에서 non-sensitive 후보 하나를 전송하고 Inbox에서 `proposed` 상태인지 확인합니다.
