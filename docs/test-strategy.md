# MVP 통합 테스트 전략

## 목적과 범위

이 문서는 Second Brain MVP가 설계 문서의 데이터 안전성, 기억 신뢰성, 장애 복구 계약을 만족하는지 검증하는 기준입니다.

아직 수집 API와 MCP 서버의 구현 언어 및 테스트 프레임워크가 정해지지 않았으므로 특정 도구의 문법이나 라이브러리를 요구하지 않습니다. 모든 테스트는 관찰 가능한 입력, 저장 상태, 출력 계약으로 작성하며 구현이 정해진 뒤 같은 테스트 ID를 유지한 채 자동화합니다.

MVP 테스트 범위는 다음과 같습니다.

- 데이터베이스 마이그레이션, 제약조건, 트랜잭션
- 인증, RLS, 주체 및 tenant 격리
- 수집 API의 멱등성과 민감정보 검사
- GitHub Issue 증분 동기화와 스냅샷 중복 제거
- 기억의 출처, 상태, 대체 관계와 실패 사례 상태
- Context Pack 및 MCP 9개 도구의 계약
- 감사 로그와 민감정보 제거
- 재시도 가능한 장애와 부분 실패 복구

벡터 검색, 실시간 webhook, 웹 관리 화면, 자동 PR 및 배포, 여러 AI의 동시 쓰기 조정은 MVP 테스트 범위에서 제외합니다.

## 테스트 원칙

1. **외부 동작을 검증합니다.** 내부 함수명이나 구현 클래스보다 API 응답, DB 상태, MCP 결과와 감사 기록을 확인합니다.
2. **빠른 하위 테스트를 우선합니다.** 가능한 규칙은 DB 계약 또는 컴포넌트 통합 테스트로 검증하고, 전체 E2E는 핵심 흐름만 둡니다.
3. **모든 테스트는 독립적이어야 합니다.** 실행 순서, 이전 테스트 데이터, 실제 시각과 외부 네트워크에 의존하지 않습니다.
4. **실제 PostgreSQL 동작을 검증합니다.** RLS, FK, unique, 트랜잭션처럼 DB 의미가 중요한 테스트를 인메모리 대체 DB로 통과시키지 않습니다.
5. **GitHub는 결정론적 대역으로 검증합니다.** CI에서 실제 GitHub 저장소, rate limit 또는 네트워크 상태에 의존하지 않습니다.
6. **재시도는 테스트 러너가 숨기지 않습니다.** 제품의 재시도와 복구 동작은 명시적인 시계, 오류 주입과 호출 횟수로 검증합니다.
7. **민감정보는 테스트 산출물에도 남기지 않습니다.** fixture는 명백한 가짜 값만 사용하며 로그, diff, trace와 오류 메시지도 제거 검사의 대상입니다.
8. **한 테스트는 한 소유 tenant 안에서 정리됩니다.** 격리 테스트만 의도적으로 두 tenant를 사용합니다.

## 테스트 수준

| 수준 | 대상 | 실행 환경 | 목적 |
|---|---|---|---|
| L0 정적 계약 | 마이그레이션 파일, API 및 MCP 스키마, fixture 형식 | DB나 서버 없이 실행 | 누락된 계약, 중복 이름, 호환되지 않는 스키마 변경을 빠르게 차단 |
| L1 DB 계약 | 마이그레이션, enum/check/FK/unique, RLS, DB 함수 및 트랜잭션 | 빈 실제 PostgreSQL 인스턴스 | 데이터 무결성과 권한 경계를 가장 가까운 계층에서 검증 |
| L2 컴포넌트 통합 | 수집 API, Context Builder, GitHub 어댑터, MCP 핸들러 | 실제 PostgreSQL + 프로세스 내부 또는 로컬 전송 계층 + 외부 서비스 대역 | 각 경계의 요청, 응답, 저장 효과와 실패 의미 검증 |
| L3 핵심 E2E | GitHub 동기화 입력부터 MCP 조회·쓰기까지 | 실제 PostgreSQL + 수집 API + 로컬 MCP 프로세스 + 가짜 GitHub 서버 | 사용자가 의존하는 전체 흐름과 계층 간 계약 검증 |
| L4 배포 스모크 | 적용된 마이그레이션, 인증과 읽기 전용 상태 확인 | 격리된 배포 환경이 있을 때만 실행 | 환경 변수, 네트워크, 배포 설정 오류 조기 발견 |

L4는 배포 환경이 생기기 전까지 필수 게이트가 아닙니다. 브라우저 UI가 없는 MVP이므로 브라우저 기반 E2E는 요구하지 않습니다.

## 공통 수용 규칙

- 성공 응답만 확인하지 않고 생성·변경된 행, 변경되지 않아야 하는 행, 감사 로그를 함께 확인합니다.
- 오류 응답은 안정적인 오류 분류, 요청 ID, 재시도 가능 여부를 제공하고 비밀값과 내부 연결 문자열을 포함하지 않아야 합니다.
- 시간에 따른 규칙은 고정된 테스트 시계로 검증합니다. 정렬 동률은 안정적인 보조 키로 결정되어야 합니다.
- 동일한 멱등성 키의 동시 요청은 순차 요청과 같은 최종 상태가 되어야 합니다.
- tenant A의 인증 주체가 tenant B의 식별자를 알고 있어도 존재 여부, 데이터, 변경 결과를 얻을 수 없어야 합니다.
- 필수 테스트의 skip, focus, 임의 재실행 통과는 성공으로 인정하지 않습니다.

## 테스트 매트릭스

### 데이터베이스 제약과 트랜잭션

| ID | 수준 | 시나리오 | 수용 기준 |
|---|---|---|---|
| DB-01 | L0/L1 | 빈 DB에 전체 마이그레이션 적용 | 모든 마이그레이션이 순서대로 한 번에 성공하고 필요한 테이블, 인덱스, RLS 정책과 DB 함수가 존재함 |
| DB-02 | L1 | 지원하지 않는 기억 종류, 상태, 범위와 실패 상태 저장 | 애플리케이션을 우회한 직접 쓰기도 DB에서 거부되고 부분 행이 남지 않음 |
| DB-03 | L1 | 필수 필드 누락, 존재하지 않는 repository/source/memory 참조, 자기 참조 입력 | `NOT NULL`, FK 또는 동등한 제약으로 거부되고 고아 행이 생기지 않음 |
| DB-04 | L1 | 외부 안정 ID와 요청 ID의 중복 삽입 | 정의된 고유 경계 안에서 두 번째 행이 생성되지 않음. 다른 tenant의 같은 외부 ID는 정책에 따라 독립적으로 허용됨 |
| DB-05 | L1 | 원본, 스냅샷, 기억, 감사 기록을 함께 쓰는 작업 중간에 오류 주입 | 트랜잭션 계약상 원자적인 데이터는 모두 rollback됨. 실패 감사 로그를 별도 트랜잭션으로 남기는 계약이라면 실패 사실만 남고 도메인 변경은 없음 |
| DB-06 | L1 | 지원되는 이전 스키마 fixture에서 최신 마이그레이션 적용 | 보존 대상 데이터와 관계가 유지되고 새 제약을 위반하는 조용한 데이터 손실이 없음. 지원 이전 버전이 정해질 때 해당 fixture를 추가함 |

### RLS와 tenant 격리

여기서 tenant는 한 사용자의 데이터 경계를 뜻합니다. 실제 스키마가 `tenant_id`, `owner_id` 또는 다른 이름을 사용해도 아래 의미를 보존해야 합니다.

| ID | 수준 | 시나리오 | 수용 기준 |
|---|---|---|---|
| AUTH-01 | L1/L2 | 인증 없이 모든 읽기·쓰기 경계 호출 | 원본, 스냅샷, 기억, 실행 기록과 감사 데이터의 읽기 및 쓰기가 거부됨 |
| AUTH-02 | L1 | tenant A 주체로 각 테이블의 tenant B 행을 ID 직접 조회 및 목록 조회 | 모든 경로에서 B의 행이 0건으로 보이며 join, view, 함수와 검색 결과로 우회할 수 없음 |
| AUTH-03 | L1 | tenant A 주체로 tenant B의 repository/source를 참조해 insert, update, delete | 작업이 거부되고 A와 B 양쪽 데이터가 변경되지 않음 |
| AUTH-04 | L1/L2 | tenant A와 B가 같은 repository ID, issue 번호, 멱등성 키 또는 session ID 사용 | 고유성, 중복 제거와 조회 결과가 tenant 경계를 넘지 않음 |
| AUTH-05 | L2 | GitHub 동기화 주체와 MCP 주체가 허용 범위를 넘는 도구 또는 데이터에 접근 | 최소 권한 계약 밖의 작업은 거부됨. DB 관리자 자격 증명은 클라이언트 요청이나 오류에 노출되지 않음 |
| AUTH-06 | L1 | 보안 definer 함수, view 또는 저장 프로시저를 통한 접근 | 호출자의 tenant 경계가 유지되고 명시적으로 허용하지 않은 RLS 우회가 없음 |

### 멱등성과 동시성

| ID | 수준 | 시나리오 | 수용 기준 |
|---|---|---|---|
| IDEM-01 | L2 | 같은 인증 주체, 도구, 멱등성 키와 동일 payload를 순차 재전송 | 최초와 의미상 같은 결과를 반환하고 도메인 행, 스냅샷, 실행 기록이 추가 생성되지 않음 |
| IDEM-02 | L1/L2 | IDEM-01 요청을 둘 이상의 동시 호출로 실행 | 하나의 논리적 결과만 commit되고 나머지는 같은 결과를 받거나 문서화된 중복 응답을 받음 |
| IDEM-03 | L2 | 같은 멱등성 키에 다른 payload 사용 | 명시적인 키 재사용 충돌로 거부되고 최초 결과가 변경되지 않음 |
| IDEM-04 | L2 | commit 직후 응답 전달 전에 연결 오류를 주입하고 같은 요청 재시도 | 재시도가 최초 commit을 찾아 반환하며 중복 행을 만들지 않음 |
| IDEM-05 | L2 | 서로 다른 tenant 또는 서로 다른 쓰기 도구에서 같은 키 사용 | 정의된 멱등성 namespace에 따라 서로 독립 처리됨 |

### GitHub 원본과 스냅샷 중복 제거

`canonical content`는 동기화 트랙이 공개하는 정규화 규칙의 결과입니다. 해시 알고리즘 자체보다 어떤 필드와 정규화가 해시에 포함되는지를 계약으로 고정합니다.

| ID | 수준 | 시나리오 | 수용 기준 |
|---|---|---|---|
| SNAP-01 | L2 | 새 repository의 새 Issue와 댓글 수집 | 안정 ID로 원본이 생성되고 최초 스냅샷이 정확히 하나 생성됨 |
| SNAP-02 | L2 | 동일한 canonical content를 전달 시각이나 필드 순서만 바꾸어 재수집 | 원본의 동기화 메타데이터는 갱신될 수 있으나 새 내용 스냅샷은 생성되지 않음 |
| SNAP-03 | L2 | 본문, 제목, 상태, 라벨, 삭제 상태 또는 댓글 중 계약상 버전 대상 필드 하나 변경 | 변경된 엔티티에만 새 스냅샷이 정확히 하나 생성되고 이전 스냅샷은 보존됨 |
| SNAP-04 | L1/L2 | 같은 변경을 동시에 두 번 수집 | 같은 content hash의 스냅샷은 하나만 존재함 |
| SNAP-05 | L2 | 같은 issue 번호를 가진 서로 다른 repository 또는 tenant 수집 | 원본과 스냅샷이 섞이지 않으며 `repository_id + issue_number` 경계가 유지됨 |
| SNAP-06 | L2 | 오래된 GitHub 응답이 최신 스냅샷 뒤에 도착 | 최신 원본을 과거 상태로 되돌리지 않음. 과거 이벤트 보존 여부와 무관하게 현재 projection은 최신 외부 갱신 시각/버전을 유지함 |

### 기억 출처와 대체 관계

| ID | 수준 | 시나리오 | 수용 기준 |
|---|---|---|---|
| MEM-01 | L1/L2 | source 참조 없이 활성 기억(`proposed`, `confirmed`, `verified`) 생성 | 거부됨. 모든 활성 기억에서 실제 원본, 사용자 메시지 참조, 테스트/실행 결과 또는 승인 문서로 역추적 가능함 |
| MEM-02 | L1 | tenant A 기억이 tenant B source 또는 다른 repository 범위 source를 참조 | tenant 경계를 넘는 참조는 거부됨. repository 간 참조가 허용되는 경우에도 명시적 범위 정책과 감사 근거가 필요함 |
| MEM-03 | L2 | `brain_get_detail`로 기억 상세 조회 | 기억의 상태, 범위, source ID/URI/excerpt, 대체 관계와 검증 이력이 계약대로 반환됨 |
| MEM-04 | L2 | AI 추론을 확정 근거 없이 저장 | `proposed`만 허용되고 기본 Context Pack과 일반 검색에서 제외됨 |
| MEM-05 | L2 | 사용자 명시 결정 및 테스트로 검증된 해결 저장 | 각각 `confirmed`, `verified` 조건을 만족하는 근거가 있을 때만 해당 상태가 허용됨 |
| SUPER-01 | L1/L2 | `brain_supersede_memory`로 기존 기억 A를 신규 기억 B로 교체 | 한 트랜잭션에서 A는 `superseded`, B는 활성 상태가 되고 A→B 및 B→A 방향의 관계가 일관되게 조회됨 |
| SUPER-02 | L1/L2 | 존재하지 않는 기억, 자기 자신, 다른 tenant 기억, 이미 모순된 체인으로 교체 | 전체 작업이 거부되고 기존 상태와 관계가 유지됨 |
| SUPER-03 | L1/L2 | A→B→A 순환 또는 한 기억을 상충하는 두 활성 기억으로 동시에 교체 시도 | 순환 및 모호한 활성 후속 관계가 거부됨 |
| SUPER-04 | L2 | 일반 검색과 Context Pack에서 superseded/deprecated/deleted 기억 조회 | 기본 결과에서 제외되고 상세/이력 조회처럼 명시한 경로에서만 반환됨 |
| CONFLICT-01 | L2/L3 | 같은 tenant와 같은 scope에 상충하는 활성 기억 두 개 배치 | Context Builder가 하나를 임의 선택하지 않고 두 기억과 근거를 `conflicts`에 반환함 |

### 실패 사례 상태

| ID | 수준 | 시나리오 | 수용 기준 |
|---|---|---|---|
| FAIL-01 | L1/L2 | 증상만 있는 실패 저장 | 실패 해결 상태는 `observed`이며 원인이나 해결법을 검증된 사실로 표시하지 않음 |
| FAIL-02 | L1/L2 | 조사, 가설, 미검증 해결, 검증 완료 순서로 갱신 | `investigating`/`hypothesis`/`resolved`/`verified` 의미와 필수 근거가 유지됨. `verified`에는 테스트 또는 재현 근거가 필요함 |
| FAIL-03 | L1/L2 | 검증된 해결이 다시 실패한 사실 저장 | 상태가 `recurring`으로 바뀌고 이전 검증 근거와 재발 근거가 모두 보존됨 |
| FAIL-04 | L1/L2 | 근거 없이 `verified`, 유효하지 않은 상태값 또는 정책상 금지한 상태 전이 요청 | 거부되고 기존 상태가 유지됨 |

## 핵심 E2E 시나리오

L3에는 다음 네 흐름만 필수로 둡니다. 나머지 경계값은 L1과 L2에서 검증합니다.

### E2E-01: GitHub 학습 기록 조회

1. 가짜 GitHub가 새 Issue와 댓글을 두 페이지로 반환합니다.
2. 동기화가 수집 API를 통해 원본과 최초 스냅샷을 저장합니다.
3. 같은 fixture를 재실행해 중복이 없음을 확인합니다.
4. `brain_get_context`와 `brain_get_detail`로 repository 범위의 학습 기억과 출처를 조회합니다.
5. tenant B 클라이언트에는 결과가 보이지 않음을 확인합니다.

### E2E-02: 결정 저장과 교체

1. AI 제안 결정을 저장해 `proposed`와 Inbox 제외/포함 규칙을 확인합니다.
2. 사용자의 명시적 결정을 저장해 `confirmed`임을 확인합니다.
3. 신규 결정으로 교체해 기존 기억과 신규 기억의 양방향 provenance를 확인합니다.
4. 일반 Context Pack에는 신규 결정만 적용됨을 확인합니다.

### E2E-03: 실패 사례 검증과 재발

1. 증상을 `observed`로 저장합니다.
2. 가설과 미검증 해결을 차례로 기록합니다.
3. 테스트 근거와 함께 `verified`로 변경합니다.
4. 같은 문제가 재발한 근거를 저장해 `recurring`이 되고 Context 결과가 가설과 검증 이력을 구분하는지 확인합니다.

### E2E-04: 응답 유실 후 복구와 감사

1. 쓰기가 commit된 직후 응답을 유실시킵니다.
2. 같은 멱등성 키로 재시도합니다.
3. 한 개의 도메인 결과와 재시도 이력이 남는지 확인합니다.
4. 입력에 넣은 합성 비밀 표식이 DB, 로그와 테스트 산출물 어디에도 없는지 전체 검색합니다.

## Fixture 원칙

### 기본 데이터 세트

모든 fixture는 다음 최소 구성을 재사용할 수 있어야 합니다.

```text
tenant A
  사용자 주체 A
  GitHub 동기화 주체 A
  MCP 주체 A
  repository A1
    issue 101, comment 1001
    source와 snapshot
    proposed/confirmed/verified 기억
    observed/verified 실패 사례

tenant B
  사용자 주체 B
  repository B1
    tenant A와 의도적으로 같은 issue 번호와 멱등성 키
```

### 작성 규칙

- UUID, repository ID, issue 번호, 시각과 hash 기대값은 고정합니다. `now`, 무작위 값과 실제 사용자 계정을 사용하지 않습니다.
- 기본 시각과 GitHub `updated_at`은 순서와 동률을 모두 시험할 수 있도록 명시합니다.
- fixture는 작은 조각으로 합성하고, 한 테스트가 필요한 차이만 override합니다.
- 각 활성 기억 fixture에는 실제로 존재하는 source와 tenant가 일치하는 provenance를 포함합니다. 잘못된 provenance는 음성 테스트 안에서만 만듭니다.
- GitHub fixture는 원본 HTTP 요청/응답 의미, pagination, cursor, rate-limit/5xx/4xx와 재시도 순서를 표현할 수 있어야 합니다.
- canonical content fixture는 원본 입력, 정규화 결과, 포함 필드와 예상 hash를 한 세트로 버전 관리합니다.
- MCP 계약 fixture는 각 도구의 최소 유효 입력·출력, 최대 경계와 대표 오류를 포함하며 구현 언어의 타입 정의를 원본으로 삼지 않습니다.
- 민감정보 fixture는 `TEST_ONLY_SECRET_DO_NOT_USE`처럼 실제 자격 증명과 혼동할 수 없는 표식을 사용합니다. 표식 전체가 산출물에서 발견되지 않아야 합니다.
- 테스트 종료는 transaction rollback, 격리 schema 또는 고유 tenant namespace 중 하나로 보장합니다. 행 삭제 순서에 의존하는 전역 cleanup은 피합니다.
- golden fixture는 의미 있는 계약 필드만 포함합니다. DB 자동 시각, 실행 순서와 무관한 ID까지 전체 응답을 snapshot으로 고정하지 않습니다.
- 운영 DB dump, 실제 Issue 전문과 실제 로그를 fixture로 반입하지 않습니다.

## 오류 주입 기준

통합 테스트는 최소한 다음 지점에 한 번만 발생하거나 반복되는 오류를 주입할 수 있어야 합니다.

- DB transaction 시작 전, domain write 중간, commit 직후
- 감사 기록 전과 후
- 수집 API가 GitHub 동기화 payload를 받기 전과 commit 후 응답 전
- GitHub pagination의 첫 페이지, 중간 페이지와 마지막 페이지
- Context Builder 조회 중
- MCP transport 연결 전, 요청 처리 중과 응답 직전

오류 주입은 제품 코드의 실제 오류 분류 경로를 통과해야 하며 테스트 안에서 DB 상태를 직접 조작해 성공한 것처럼 만들지 않습니다.

## 다른 트랙이 제공해야 할 test hooks

### A 트랙: DB 스키마와 마이그레이션

- 빈 DB와 지원 이전 버전에 마이그레이션을 적용하는 단일 진입점
- RLS를 실제로 통과하는 `anonymous`, tenant 사용자, GitHub 동기화, MCP 및 운영 주체의 테스트 자격 증명 생성 방법
- DB 관리자 우회 없이 tenant A/B를 seed하고 주체를 전환하는 방법
- 모든 enum/check/FK/unique/index/RLS 정책과 보안 definer 함수 목록
- 원자성 경계와 감사 로그가 별도 트랜잭션인지에 대한 계약
- tenant별 데이터 정리 또는 격리 schema 생성 진입점
- migration 적용 버전과 schema fingerprint를 읽는 방법

### B 트랙: 수집 API와 인증 계약

- 기계 판독 가능한 요청·응답·오류 스키마와 안정적인 오류 코드
- 테스트 전용 인증 주체 발급 또는 서명 대역. 운영 비밀은 필요하지 않아야 함
- 멱등성 namespace, payload fingerprint, 보존 기간과 키 재사용 충돌 의미
- commit 직후 응답 유실을 포함한 명명된 오류 주입 지점
- 고정 시계와 요청 ID 공급자를 주입하는 경계
- 민감정보 탐지기를 독립 검증할 입력 경계와 제거된 감사 payload 관찰 방법
- 원본/스냅샷/기억/실행 기록 쓰기의 transaction 경계

### C 트랙: GitHub 동기화와 MCP 계약

- 실제 네트워크 대신 pagination, cursor, rate limit와 오류 순서를 제공할 GitHub transport 경계
- backoff 대기 없이 호출 횟수와 예정 지연을 관찰할 시계 및 sleeper 경계
- canonical content 생성 규칙, hash 계약과 버전 대상 필드 목록
- 마지막 성공 cursor, overlap window, partial failure checkpoint를 읽을 방법
- 9개 MCP 도구의 버전 관리된 기계 판독 입출력 스키마
- MCP를 실제 로컬 전송 방식으로 시작하고 준비 상태를 확인하며 종료하는 진입점
- Context Pack의 항목 수·예산·정렬 이유와 제외 이유를 테스트에서 관찰할 구조화 메타데이터
- Codex형 및 Claude형 클라이언트가 공유할 transport-neutral contract fixture

test hook은 운영에서 활성화되는 숨은 관리자 endpoint가 아니어야 합니다. 의존성 주입, 테스트 전용 프로세스 구성 또는 격리된 DB fixture로 제공하고 production build에서 외부 호출이 불가능해야 합니다.

## CI 단계와 게이트

### 1. 정적 계약

- 문서와 기계 판독 스키마 형식 검증
- 마이그레이션 순서와 중복 이름 검사
- MCP 9개 도구 목록과 계약 fixture 일치 검사
- 실제 외부 네트워크 호출 금지 검사

실패 시 이후 단계를 실행하지 않습니다.

### 2. DB 계약

- 매 실행마다 빈 실제 PostgreSQL 인스턴스 생성
- 최신 마이그레이션 적용
- DB-*, AUTH-*의 L1, SUPER-*의 L1과 감사 권한 테스트 실행
- 지원 이전 버전 fixture가 생기면 upgrade 테스트 실행

테스트는 병렬화할 수 있지만 각 worker는 독립 DB/schema/tenant namespace를 가져야 합니다.

### 3. 컴포넌트 통합

- 실제 PostgreSQL 위에서 수집 API, Context Builder, GitHub 어댑터와 MCP 핸들러 실행
- 외부 GitHub와 시간/대기는 결정론적 대역 사용
- IDEM-*, SNAP-*, MEM-*, FAIL-*, GH-*, MCP-*와 AUD-* 실행
- 오류 응답과 로그에 합성 비밀 표식이 없는지 검사

영역별 shard는 허용하지만 한 테스트 파일 안의 순서 의존은 허용하지 않습니다.

### 4. 핵심 E2E

- 실제 로컬 프로세스 경계로 E2E-01부터 E2E-04 실행
- 서로 다른 두 tenant 인증 주체 사용
- 테스트 러너 재시도 없이 실행
- 실패 시 제거된 요청/응답, DB 진단과 프로세스 로그만 산출물로 보존

### 5. 배포 스모크

배포 환경이 생긴 뒤에만 별도 승인된 격리 tenant로 실행합니다.

- schema version과 준비 상태 확인
- 비인가 접근 거부
- 격리 tenant에서 생성-조회-삭제 가능한 최소 합성 기록
- 실제 GitHub 쓰기와 운영 사용자 데이터 접근 금지

## CI 안정성 정책

- 고정 sleep을 사용하지 않고 상태, 가짜 시계 또는 명시적 완료 신호를 기다립니다.
- 제품 retry 검증을 제외한 자동 테스트 재시도는 기본적으로 0입니다.
- flaky 테스트는 필수 게이트에서 조용히 제외하지 않습니다. 원인과 소유자를 기록하고 격리 여부를 명시합니다.
- 실패 산출물은 짧은 보존 기간을 사용하고 secret scan을 통과한 뒤 업로드합니다.
- 병렬 실행에서도 같은 고정 ID를 쓸 수 있도록 DB 경계를 worker별로 격리합니다.
- 네트워크 비결정성, 실제 GitHub rate limit, 현재 시각과 locale에 따른 결과 차이를 허용하지 않습니다.

## MVP 최종 수용 기준

다음 조건을 모두 만족해야 해당 구현 단계를 완료로 판단합니다.

- 빈 DB와 지원되는 이전 schema에서 필수 마이그레이션 및 DB 계약 테스트가 통과함
- 두 tenant를 사용한 모든 RLS/격리 테스트가 관리자 우회 없이 통과함
- 순차·동시·응답 유실 재시도에서 논리적 쓰기 결과가 하나임
- 동일 canonical content에는 스냅샷이 추가되지 않고 의미 있는 변경에만 하나 추가됨
- 모든 활성 기억이 tenant가 일치하는 근거로 역추적됨
- 대체 관계에 순환이나 모호한 활성 후속 기억이 없고 이전 이력이 보존됨
- 실패 가설, 미검증 해결과 검증된 해결이 상태와 근거로 구분됨
- GitHub 부분 실패 다음 실행이 누락과 중복 없이 최종 상태로 수렴함
- MCP 9개 도구가 같은 기계 판독 계약을 만족하고 장애를 정상 빈 결과나 성공으로 위장하지 않음
- 모든 쓰기가 감사되며 합성 비밀 표식이 DB, 응답, 로그와 CI 산출물에서 0회 발견됨
- E2E-01부터 E2E-04가 테스트 러너 재시도와 실제 외부 네트워크 없이 통과함
- 필수 테스트에 skip/focus가 없고 알려진 비결정적 실패가 없음

구현 세부사항이 바뀌어도 이 테스트 ID와 관찰 가능한 수용 의미를 유지합니다. 계약 변경이 필요하면 구현과 테스트를 함께 조용히 바꾸지 않고 관련 설계 문서의 결정을 먼저 갱신합니다.
